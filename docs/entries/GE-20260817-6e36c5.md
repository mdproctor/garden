## Gizmo-generated @GraphQLApi classes invisible to SmallRye GraphQL schema builder

**ID:** GE-20260817-6e36c5
**Stack:** Quarkus 3.x, SmallRye GraphQL, Gizmo, Jandex
**Symptom:** A Gizmo-generated class annotated with `@GraphQLApi` exists as a fully functional CDI bean (injectable, interceptable), but SmallRye GraphQL logs `SRGQL010000: Schema is null, or it has no operations`. The GraphQL schema contains none of the operations defined in the generated class. No compile error, no startup error beyond the schema warning.
**Context:** Building a Quarkus extension that uses `GeneratedBeanBuildItem` (Gizmo bytecode generation) to produce `@GraphQLApi` resolver classes at build time. The generated classes are valid CDI beans and can be injected via `Instance<>`, but SmallRye GraphQL does not discover them.

### What was tried (didn't work)
- Verified the generated class has correct `@GraphQLApi`, `@Query`, `@Mutation` annotations — all present in bytecode
- Confirmed the class is a valid CDI bean via `Arc.container().instance()` — works
- Checked SmallRye GraphQL logs for annotation scanning errors — none; the class simply never appears in the scan
- Tried adding `@ApplicationScoped` explicitly alongside `@GraphQLApi` — no effect on discovery

### Root cause
SmallRye GraphQL's schema builder discovers annotated classes by scanning the Jandex index (`IndexView`) produced during Quarkus augmentation. `GeneratedBeanBuildItem` classes produced by Gizmo are bytecode-only — they are injected directly into the CDI container but are never added to the Jandex index. SmallRye GraphQL only looks at the Jandex index for `@GraphQLApi` annotations, so Gizmo-generated classes are completely invisible to it regardless of their CDI status.

### Fix
Use APT (annotation processing) source generation instead of Gizmo bytecode generation. APT generates `.java` source files during compilation. These source files are compiled by `javac` in the normal compilation phase, and the resulting `.class` files are picked up by the `jandex-maven-plugin` and added to the Jandex index. SmallRye GraphQL then discovers them normally.

```java
// In an AbstractProcessor, generate source:
JavaFileObject file = processingEnv.getFiler().createSourceFile(fqcn);
try (Writer writer = file.openWriter()) {
    writer.write(generatedSource);
}
// The generated .java file gets compiled -> Jandex-indexed -> SmallRye discovers it
```

Do NOT use Gizmo for any class that needs to be discovered by SmallRye GraphQL, MCP server scanners, or any other Quarkus extension that relies on Jandex annotation scanning.

### Alternatives considered
- Adding generated classes to the Jandex index manually via a custom build step — Quarkus does not expose an API for injecting synthetic entries into the application's Jandex index after augmentation
- Using `AdditionalIndexedClassesBuildItem` — only works for classes that exist on the classpath as `.class` files before augmentation, not for Gizmo-generated bytecode

### Why this is non-obvious
The misleading part is that Gizmo-generated classes work perfectly as CDI beans. `Instance<MyGeneratedResolver>` resolves, interceptors fire, `@Inject` works. The mental model "if CDI can see it, other Quarkus extensions can see it" is wrong — CDI and Jandex are separate discovery mechanisms, and SmallRye GraphQL uses Jandex exclusively. The symptom (schema is null) gives no indication that the class exists but is invisible to the scanner.

### Why this fix
APT source generation is the correct tool because it operates at the right phase of the build lifecycle. Gizmo runs during Quarkus augmentation (after Jandex indexing), while APT runs during compilation (before Jandex indexing). The generated `.java` files follow the normal compile -> index -> discover pipeline that all other source-level classes use.
