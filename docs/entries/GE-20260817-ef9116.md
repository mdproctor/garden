## @Remotable naming collision with kie-api on transitive classpath

**ID:** GE-20260817-ef9116
**Stack:** kie-api 10.1.0, Quarkus 3.x
**Symptom:** IDE auto-import silently selects `org.kie.api.remote.Remotable` instead of the project's own `@Remotable` annotation. Code compiles without error but runtime behaviour is wrong — the annotation has no effect because the framework scanning looks for the project's annotation, not KIE's.
**Context:** A project defines its own `@Remotable` annotation with `@Target(TYPE)` and remote-invocation semantics. The project also has KIE/Drools on the transitive classpath (e.g. via `kie-api:10.1.0`), which defines `org.kie.api.remote.Remotable` with `@Target(TYPE)` and similar remote-invocation semantics.

### What was tried (didn't work)
- Noticed at runtime that annotated classes were not being discovered by the callback proxy framework
- Checked annotation presence via reflection — annotation was present but was the wrong `Remotable` (KIE's, not the project's)
- IDE showed no warning or ambiguity indicator during import resolution

### Root cause
Both `org.kie.api.remote.Remotable` and the project's `@Remotable` share the same simple name, same `@Target(TYPE)`, and similar semantic intent (remote invocation eligibility). IDEs (IntelliJ, Eclipse) resolve ambiguous auto-imports by classpath order or alphabetical package name. `org.kie.api.remote` sorts before most project packages alphabetically, so it wins the auto-import silently.

### Fix
Rename the project annotation to avoid the collision entirely. In the casehub-platform case, `@Remotable` was renamed to `@CallbackEligible`:

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface CallbackEligible {
    // No collision with any known library annotation
}
```

The rename eliminates the ambiguity permanently. Updating all usages is a straightforward find-and-replace.

### Alternatives considered
- Adding the correct import manually and relying on developers to not accept auto-import suggestions — fragile, every new file risks the same mistake
- Excluding `kie-api` from the classpath — not feasible when Drools is a core dependency

### Why this is non-obvious
The collision is silent. The code compiles, the annotation is present at runtime, and no warning is emitted. The only symptom is that the framework ignores the annotated classes because it scans for the project's annotation FQN, not KIE's. Debugging requires checking the actual import statement, which is easy to overlook when the annotation name matches expectations.
