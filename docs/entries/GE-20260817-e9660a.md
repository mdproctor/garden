## Jandex indexes readable from APT classloader for cross-module annotation discovery

**ID:** GE-20260817-e9660a
**Stack:** Maven, jandex-maven-plugin, javax.annotation.processing
**Labels:** `#annotation-processing` `#cross-module` `#build-tooling`
**What it achieves:** Enables an APT processor to discover annotations across all dependency JARs — not just the current compilation unit — by reading pre-built Jandex indexes from the compilation classpath.
**Context:** When writing an `AbstractProcessor` that needs to generate code based on annotations in dependency modules (e.g. generating a resolver class that references SPIs annotated in `platform-api`), the standard `roundEnv.getElementsAnnotatedWith()` only sees annotations in the current compilation unit. Cross-module discovery requires a different mechanism.

### The technique

Each Maven module that uses `jandex-maven-plugin` produces a `META-INF/jandex.idx` file in its JAR. During APT compilation, the processor's classloader has all dependency JARs on the classpath. This means `getClass().getClassLoader().getResources("META-INF/jandex.idx")` returns an `Enumeration` of all Jandex indexes from all dependencies:

```java
public class MyProcessor extends AbstractProcessor {

    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment roundEnv) {
        if (roundEnv.processingOver()) return false;

        try {
            Enumeration<URL> indexes = getClass().getClassLoader()
                .getResources("META-INF/jandex.idx");

            while (indexes.hasMoreElements()) {
                URL url = indexes.nextElement();
                try (InputStream is = url.openStream()) {
                    IndexReader reader = new IndexReader(is);
                    Index index = reader.read();

                    // Now scan for any annotation across that dependency
                    Collection<AnnotationInstance> found =
                        index.getAnnotations(DotName.createSimple("io.casehub.platform.api.SomeAnnotation"));
                    // Generate code based on discovered annotations
                }
            }
        } catch (IOException e) {
            processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, e.getMessage());
        }
        return false;
    }
}
```

This gives the APT processor the same cross-module annotation visibility that Quarkus augmentation has via its own Jandex scanning — but at the compilation phase, so generated source files get compiled and Jandex-indexed themselves.

### Alternatives considered
- Using Quarkus augmentation (Gizmo) for cross-module discovery — produces bytecode that is NOT Jandex-indexed, so generated classes are invisible to other extensions that scan Jandex (see GE-20260817-6e36c5)
- Using `ServiceLoader` patterns to discover implementations at runtime — does not provide compile-time code generation capability; discovery happens too late

### Why this is non-obvious
Most developers think of APT as limited to the current compilation unit. The idea that you can enumerate classloader resources during annotation processing to read pre-built indexes from dependencies is not documented in either the APT or Jandex documentation. It works because APT processors run inside `javac`, which sets up a classloader with all compile-scope dependencies.

### When to use it
When you need to generate source code based on annotations that exist in dependency modules, and the generated code must itself be discoverable via Jandex (e.g. for SmallRye GraphQL, MCP server scanning, or any Quarkus extension that uses Jandex). This is the alternative to Quarkus augmentation when Jandex visibility of the generated output matters.
