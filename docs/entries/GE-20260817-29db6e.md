## APT over Gizmo when generated classes need Jandex discovery

**Topic:** Code generation strategy — APT vs Gizmo based on Jandex discovery requirement
**Alternatives exist:** yes — Gizmo bytecode generation is the alternative (valid when only CDI discovery is needed)

### The convention

Choose the code generation strategy based on what needs to discover the generated classes:

| Discovery requirement | Strategy | Why |
|-----------------------|----------|-----|
| Only CDI (`Instance<>`, `@Inject`, bean manager) | **Gizmo** | Bytecode → `GeneratedBeanBuildItem` → CDI container. Fastest, no source files. |
| Jandex annotation scanning (SmallRye GraphQL, MCP scanner, custom extension scanners) | **APT** | `.java` source → compiled → Jandex-indexed → discoverable by any extension that scans the index. |
| Both CDI and Jandex | **APT** | APT-generated classes get both: Jandex-indexed by the build plugin, and registered as CDI beans by the normal `@ApplicationScoped` / `@GraphQLApi` discovery path. |

The decision tree is simple: if any Quarkus extension besides CDI itself needs to find your generated class via annotation scanning, use APT. Otherwise Gizmo is fine.

### Why this style

The build lifecycle ordering makes this deterministic:

1. **APT** runs during `javac` compilation (Maven `compile` phase)
2. **Jandex indexing** runs after compilation (Maven `process-classes` phase via `jandex-maven-plugin`)
3. **Quarkus augmentation** runs after indexing (via `quarkus-maven-plugin:build`)
4. **Gizmo** bytecode generation happens during augmentation (step 3)

APT output (step 1) is available for Jandex indexing (step 2). Gizmo output (step 4) is not — it arrives after the Jandex index is sealed. This is not a bug; it is the fundamental lifecycle ordering of the Quarkus build.

### Trade-offs

APT source generation:
- **Pro:** Generated classes are fully visible to all discovery mechanisms (Jandex, CDI, SmallRye, custom scanners)
- **Pro:** Generated source is human-readable and debuggable
- **Con:** More verbose to write than Gizmo (string-based source generation vs bytecode API)
- **Con:** Requires careful handling of incremental compilation

Gizmo bytecode generation:
- **Pro:** Concise API, no string-based source manipulation
- **Pro:** Tight integration with Quarkus augmentation pipeline
- **Con:** Generated classes are invisible to Jandex and any extension that relies on annotation index scanning
- **Con:** Bytecode is harder to debug than generated source

### When not to use it

If the generated class is purely an internal CDI bean (e.g. a producer method, a synthetic decorator, an internal service) that no other extension needs to discover, Gizmo is the right choice. It is simpler, faster, and has first-class Quarkus augmentation support. The APT convention only applies when cross-extension discovery via Jandex is a requirement.
