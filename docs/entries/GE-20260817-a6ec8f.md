## CDI @Decorator for callback proxies — avoids displacement ladder with multiple deployment scenarios

**ID:** GE-20260817-a6ec8f
**Stack:** Quarkus 3.x, CDI 4.0
**Labels:** `#cdi-patterns` `#deployment-flexibility`
**What it achieves:** Enables a single decorator to transparently route SPI calls to either a local implementation, a remote callback proxy, or a no-op default — without requiring the callback module to displace any existing CDI bean.
**Context:** When building a callback proxy system (e.g. remote invocation of an SPI over HTTP/MCP), the proxy module must coexist with three deployment scenarios: (1) no local implementation and no callbacks configured, (2) no local implementation but callbacks configured, (3) a local `@ApplicationScoped` implementation exists. Using `@Alternative @Priority` for the proxy creates a displacement ladder problem — the proxy must pick a priority that beats the `@DefaultBean` but not the local impl, and this breaks when new alternatives are added.

### The technique

Use `@Decorator @Priority(APPLICATION + 100)` to wrap whatever CDI selects as the delegate. The decorator intercepts every call and decides whether to delegate locally or route remotely:

```java
@Decorator
@Priority(Interceptor.Priority.APPLICATION + 100)
public class CallbackSpiDecorator implements SomeSpi {

    @Inject @Delegate @Any
    SomeSpi delegate;

    @Inject
    CallbackRegistry callbackRegistry;

    @Override
    public Result doWork(Request request) {
        Optional<CallbackEndpoint> callback = callbackRegistry.resolve(request);
        if (callback.isPresent()) {
            return callback.get().invoke(request);
        }
        return delegate.doWork(request);
    }
}
```

The three deployment scenarios all work without any priority tuning:

1. **No local impl + no callbacks:** Decorator wraps the `@DefaultBean` no-op. `callbackRegistry.resolve()` returns empty. Delegate (no-op) is called. Result: silent no-op.
2. **No local impl + callbacks configured:** Decorator wraps the `@DefaultBean` no-op. `callbackRegistry.resolve()` returns the remote endpoint. Remote is called. Result: callback proxy works.
3. **Local impl exists:** Decorator wraps the local `@ApplicationScoped` bean. `callbackRegistry.resolve()` returns empty (no callback configured for locally-implemented SPIs). Delegate (local impl) is called. Result: local implementation used as-is.

### Alternatives considered
- `@Alternative @Priority(N)` proxy bean — requires careful priority arithmetic; breaks when a third deployment scenario adds another alternative. The displacement ladder problem: priority N must beat `@DefaultBean` (priority 0) but lose to any local `@ApplicationScoped` impl — but `@ApplicationScoped` has no inherent priority, so the proxy always wins and the local impl is displaced.

### Why this is non-obvious
The decorator pattern in CDI is typically taught as a way to add cross-cutting concerns (logging, metrics). Using it as a routing mechanism that decides between local and remote invocation is an architectural pattern, not a textbook decorator use case. The key insight is that `@Decorator` wraps the *selected* bean — it does not participate in bean selection. This makes it orthogonal to the `@Alternative`/`@DefaultBean`/`@Priority` selection mechanism, which is exactly what avoids the displacement ladder.

### When to use it
When a module needs to intercept an SPI and conditionally route to an alternative implementation (especially a remote proxy) without displacing whatever CDI selected as the primary bean. Follows the precedent set by `agent-gate` in casehub-platform (PP-20260808-340f01), which uses `@Decorator @Priority(APPLICATION)` to wrap `RoutingAgentProvider` with rate limiting.
